Chapter 02 · The mathematical foundation

Two ways to apply the same operator

The assembled method builds the big global matrix first. The matrix-free method computes each element's local contribution and accumulates it directly into the result.

Assembled pipeline

Store global K
K = Σₑ Aₑᵀ Kₑ Aₑ
y = Kp

First add all local element matrices into the global sparse matrix K. Then perform a global sparse matrix-vector product.

Matrix-free pipeline

No global K
y = Σₑ Aₑᵀ(Kₑ(Aₑp))Aₑ selects the global DOFs belonging to element e.

For each element: gather its input values, apply its local stiffness matrix, then add the result into the global output.

Matrix-free does not mean “no matrices.” The local element matrix Kₑ can still be stored. The global matrix K is what we avoid explicitly assembling.
Chapter 03 · One element's journey

Gather → local multiply → scatter

Select each stage to inspect what data it reads, what it calculates, and what it writes. The local calculation is small; assembling its contributions correctly is the subtle part.

Gather: select this element's DOFs

Global memory reads

What this stage means

The connectivity table edof[e, :] lists global indices for one element. Use those indices to gather its local vector uₑ.

uₑ[j] = p[edof[e,j]]
Input p, edofOutput uₑ ∈ R²⁴
Gather is an indexed read: neighboring lanes may request different global addresses. Access pattern and cache behavior matter.

Conceptual 2D mesh view: neighboring elements share nodes, so local element vectors overlap in their global origins.

CUDA threads need a unique global index. This is the usual one-dimensional launch formula.

Chapter 06 · GPU execution choices

Where should each piece of data live?

Fusion is a data-placement decision. Keep short-lived per-element values on-chip; use shared memory to reuse the matrix; retain global memory for the mesh-wide vectors and connectivity.

Memory hierarchy

Registers private to each thread · local uₑ and fₑ
↕
Shared memory cooperatively loaded Kₑ · shared within a block
↕
L1 / L2 cache may satisfy accesses without DRAM
↕
Global memory / DRAM global p, y, edof, intermediate arrays

These are different storage spaces, not a simple literal pipeline. Caches sit alongside the memory system and can change the traffic that reaches DRAM.

Try a thread mapping

Simple ownership

One thread owns one element and computes all local rows. It is straightforward to reason about but may perform more serial work per thread and need many registers.

Benchmark against the other mappings: simplicity does not guarantee the fastest kernel.
What the paper actually implements: the fused FP32 kernel uses one thread per element and 128 threads per block. The shared reference matrix is 24 × 24 × 4 = 2,304 bytes (2.25 KiB) per block. One copy is cooperatively loaded and then reused by threads in that block. The warp-per-element and multi-element mapping buttons above are alternative designs to benchmark, not descriptions of the paper’s FP32 kernel.
A good experiment changes one design dimension at a time: thread mapping, memory layout, block size, or scatter strategy. Otherwise you cannot explain why a result changed.

Chapter 08 · The mechanics + optimization model

Why does the element stiffness change?

The paper is not only about a fast matrix-vector product. It applies that operator repeatedly inside 3D minimum-compliance topology optimization. This chapter connects the material model to the kernel's scalar factor.

The design problem

Paper §3.1 · p.7
minρ c = fᵀu
subject to K(ρ)u = f
mean(ρ) = Vf,   ρmin ≤ ρₑ ≤ 1

The design variable ρₑ assigns a material density to every element. The state variable u is the displacement solution. Compliance fᵀu is the objective used in the paper; the volume-fraction constraint limits how much material can remain.

Topology optimization is an outer design loop wrapped around a linear elasticity solve. The Kp kernel accelerates a hot part of that solve, not every operation in the whole algorithm.

The displacement field is found from K(ρ)u=f. Conjugate Gradient repeatedly calls the matrix-free Kp operator; this is where gather–GEMM–scatter is on the critical path.

Density regularization

ρ̄ₑ = filter(ρ)
ρ̃ₑ = [tanh(βη)+tanh(β(ρ̄ₑ−η)] / [tanh(βη)+tanh(β(1−η))]

The paper uses a cone density filter and a smoothed Heaviside projection with η = 0.5. The projection parameter β follows a continuation schedule.

mean(ρ) = Vf

The OC update adjusts density using analytic sensitivities and bisection so the volume constraint is enforced. The paper varies the penalty, projection sharpness, filter radius, and move limit over phases.

Chapter 10 · Solver behavior

A faster matvec is not the same as a faster solve

Conjugate Gradient (CG) repeatedly applies the stiffness operator. The preconditioner determines how many iterations are needed, so solver quality and kernel speed have to be optimized together.

PCG loop in plain language

Residual r = f − Ku
↓ apply preconditioner
z = M⁻¹r
↓ compute search direction
Update u, r, p using CG dot products
↓
Call Kp again and test residual

This sketch is conceptual: a complete PCG iteration also contains scalar dot products and recurrence updates.

Why Jacobi is simple—and limited

M = diag(K)
z = M⁻¹r

The paper forms the diagonal by a separate matrix-free element pass. Jacobi is easy to parallelize and cheap, but it does not sufficiently improve conditioning for difficult geometries and load cases.

Warm-start

Use u from design iteration k to initialize iteration k+1. The paper enables this in the main cantilever/torsion SIMP-120 studies because designs evolve gradually after early iterations.

Stopping rule

‖rₖ‖ / ‖f‖ ≤ 10⁻⁵

Stop when the unpreconditioned relative residual reaches the target or when 1,000 iterations are reached.

Why caps matter

A run that reaches its iteration cap is a useful stress test, but its final linear solve may not have converged. The paper explicitly calls out capped 2M/4.9M/8M FEA and hard-case rows.

A central result of the paper: after the operator is made fast, the Jacobi preconditioner becomes the next system-level bottleneck. Faster Kp does not remove a large CG iteration count.
Source: paper §3.5–3.6, §4.4–4.5, §5.4–5.5.

Chapter 15 · The central numerical lesson

Tensor Core throughput is not enough

The paper's most important negative result is that BF16 matrix arithmetic is fast, but BF16 inside the tested CG / iterative-refinement solve is too inaccurate for the conditioning of these stiffness systems.

Chapter 17 · What the paper does—and does not—claim

The next bottleneck is the solver, not only the kernel

The paper positions itself as an implementation-focused, single-consumer-GPU study. Its broader research story is a sequence: eliminate assembly, fuse memory movement, then improve preconditioning to reach harder/larger cases.

Research context in the paper

Classic SIMP / compact MATLAB workflowspedagogical 2D foundations
↓ scale up
3D sparse assembled solversmemory cost of global CSR becomes important
↓ matrix-free
Matrix-free element operatorsavoid global stiffness storage
↓ this paper
Fused CUDA gather–GEMM–scatterlower intermediate traffic, CuPy-native runtime compilation

The paper discusses prior work including PETSc/AMG at very large scale, GPU TO systems, matrix-free Futhark/OpenMP-C with SSOR multigrid, and matrix-free CPU geometric multigrid. Its comparisons are contextual, not hardware/preconditioner matched.

Why not claim state-of-the-art scale?

  • RTX 4090 has 24 GB VRAM and about 1.008 TB/s bandwidth; cited A100-scale studies use different hardware and larger memory capacity.
  • The closest matrix-free competitor in the paper uses a V-cycle multigrid preconditioner, while this implementation uses Jacobi-PCG.
  • Torsion hits the 1,000-iteration cap in most design iterations; MBB remains unresolved under the current solver configuration.
  • Direct fused-kernel measurements are not reported for the bridge/MBB stress table.
Comparisons need the same problem, mesh, solver, stopping criterion, precision, hardware, and timing boundary to be like-for-like.

The future-work roadmap proposed in the paper

Section 5.5 · p.31
Stage A: geometric multigrid (GMG)use mesh geometry to reduce low-frequency error
Stage B: GMG/AMG hybridthe paper proposes GMG earlier, AMG after topology condenses
Stage C: BF16 smoother experimentonly after the effective subproblem is sufficiently well conditioned

The paper proposes GMG during roughly the first 40–60 SIMP iterations, with a possible AMG transition later, then BF16 as a multigrid smoother if the effective condition number is bounded. This is a proposed direction, not a demonstrated result of the current paper.

Limit 1 · Jacobi-PCG

Iteration count dominates difficult problems; MBB does not converge adequately within the current cap.

Limit 2 · Benchmark scope

Main fused evidence is cantilever and torsion. Hard bridge/MBB evidence is FP64/FP32 baseline-only, with capped solves.

Limit 3 · BF16 accuracy

The Tensor Core variant is a throughput probe, not a valid drop-in inner solve for tested SIMP systems.

What to report for each version

Speedup = T(reference) / T(optimized)
Runtime: warm-up, repeated timing, stable summary statistics.
Correctness: absolute/relative error and solver convergence.
Resources: registers, shared memory, occupancy, atomics, memory traffic.
Reproducibility: GPU model, compiler/toolkit, launch configuration, code version.
A strong thesis result is not simply “the kernel is faster.” It explains which bottleneck changed, why the speedup happened, and what trade-off it introduced.
The takeaway

Preserve the math. Redesign the path.

Matrix-free computation avoids constructing the global stiffness matrix. Fusion then removes unnecessary intermediate transfers. Thread mapping and memory reuse make the fused computation efficient. Profiling tells you where to go next; numerical validation tells you whether the optimization is still trustworthy.
